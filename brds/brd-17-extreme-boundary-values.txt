8. Additional Notes
This BRD is the NEGATIVE TEST - EXTREME BOUNDARY VALUES scenario.
It deliberately exercises every numeric and string boundary to verify
robustness. Use this BRD to confirm:

NUMERIC BOUNDARIES:
 1. Per-Transaction Limit = 999999999999999 (15-digit, past INT32,
    into INT64) - DB column should accept this or reject with
    clear error.
 2. Negative numbers (-50000, -100) for transaction amounts and
    daily volume - should be rejected or treated as 0 by the
    parser.
 3. Zero values (Expected Monthly Volume = 0, Transaction Velocity
    can be 0) - should be handled gracefully (no division-by-zero
    in averages).
 4. Very large velocity (99999999999) - should still produce
    finite scores, not overflow.
 5. Expected Customer Count = 999999999999 - should trigger
    Large Customer Population factor without overflow.

STRING BOUNDARIES:
 6. SQL-injection-like strings in name/description fields
    (e.g., '; DROP TABLE change_requests; --) - parser must
    treat as plain text, NOT execute.
 7. XSS-like strings (e.g., <script>alert('xss')</script>,
    <img src=x onerror=alert(1)>) - must be sanitised before any
    HTML rendering.
 8. Emoji and unicode in country names (🇮🇳, 中国, ایران) -
    should be stored as-is, not crash on encoding.
 9. RTL Hebrew/Arabic text mixed with LTR English (ایران, מדינה
    ללא שם) - rendering should not break.
 10. Currency symbols from many regions in one field (€, £, ¥,
     ₹, ₩, 美元, ریال, د.إ) - should be accepted as multi-
     currency label, not parsed as numeric.

LOGIC BOUNDARIES:
 11. Velocity 0 - no "High Transaction Velocity" factor triggers
     (correct, since threshold is 5+).
 12. Velocity 5 - exactly at threshold, factor triggers.
 13. Velocity 99999999999 - factor triggers with score 80,
     weighted at 0.25 (Transaction) and 0.40 (Fraud). Should
     not overflow.
 14. Customer Segment contains SQL-injection-like text - BRD
     extraction should flag as low-confidence and not commit
     to a category.

ENUM BOUNDARIES:
 15. Criticality = 'ULTRA' (not in allowed enum) - should fall
     back gracefully or error.
 16. All booleans = True (every flag turned on) - should still
     produce a finite score, not saturate.
 17. All booleans = False - opposite, produces LOW/MINIMUM.

EXPECTED SYSTEM BEHAVIOUR:
 (a) No endpoint returns a 500 Internal Server Error.
 (b) No SQL injection succeeds (parser uses parameterised queries).
 (c) No XSS executes (frontend sanitises display).
 (d) No NaN or Infinity appears in the risk scores.
 (e) Numeric overflows either clip to INT64 max or are rejected
     with HTTP 422.
 (f) Unicode strings are stored verbatim (assuming UTF-8 DB).
 (g) The risk engine produces a finite, deterministic score even
     with garbage input.
 (h) The audit log records the upload with the original (pre-
     sanitisation) content for traceability.

This is the most comprehensive negative test - it is expected to
fail in some places and reveal edge cases that need fixing.
